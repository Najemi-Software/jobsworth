## Family: inputs

### input-undeclared

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| inputs | error | 0.1 | stable |

#### What it checks

An expression references `inputs.<name>` (or `inputs['<name>']`) but no
input called `<name>` is declared under `on.workflow_call.inputs`,
`on.workflow_dispatch.inputs`, or an action's `inputs:`.

#### Why it matters

The expression evaluates to an empty string at runtime. Nothing fails at
the reference; the empty value flows into a `with:`, an `if:`, or a
script, and the symptom appears somewhere else.

#### Example: flagged

```yaml
name: Example
on:
  workflow_call:
    inputs:
      env: {type: string}
jobs:
  deploy:
    runs-on: ubuntu-latest
    if: inputs.env == 'prod' && inputs.dry_run
    steps:
      - run: echo ok
```

#### Example: passes

```yaml
name: Example
on:
  workflow_call:
    inputs:
      env: {type: string}
      dry_run: {type: boolean}
jobs:
  deploy:
    runs-on: ubuntu-latest
    if: inputs.env == 'prod' && inputs.dry_run
    steps:
      - run: echo ok
```

#### When it does not fire

`github.event.inputs.<name>` is a different context and is not tracked.
References inside a `run:` script body are not expressions unless wrapped
in `${{ }}`.

#### Suppress

`# jobsworth-ignore input-undeclared` on the line of the expression, or
`rules: { input-undeclared: off }` in `.jobsworth.yml`.

#### Related

`input-unused`.

### input-unused

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| inputs | warning | 0.1 | stable |

#### What it checks

An input is declared but no expression anywhere in the file references it.

#### Why it matters

Callers keep passing a value nobody reads, and the declaration misleads
anyone reading the interface. Usually a leftover from a refactor.

#### Example: flagged

```yaml
name: Example
on:
  workflow_call:
    inputs:
      env: {type: string}
      verbose: {type: boolean}
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo ${{ inputs.env }}
```

#### Example: passes

```yaml
name: Example
on:
  workflow_call:
    inputs:
      env: {type: string}
      verbose: {type: boolean}
jobs:
  deploy:
    runs-on: ubuntu-latest
    if: inputs.verbose
    steps:
      - run: echo ${{ inputs.env }}
```

#### When it does not fire

Dispatch inputs of a workflow with no `workflow_call` trigger (they are
often read through `github.event.inputs`, which is not tracked), and
inputs of non-composite actions (their implementation is never inspected).

#### Suppress

`# jobsworth-ignore input-unused` on the input's line, or
`rules: { input-unused: off }` in `.jobsworth.yml`.

#### Related

`input-undeclared`.

### input-default-type

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| inputs | error | 0.1 | stable |

#### What it checks

A declared `default:` cannot be represented in the declared `type:`: a
non-numeric default for `number`, anything but a bare `true`/`false` for
`boolean`, or a `choice` default outside `options:`.

#### Why it matters

GitHub rejects the workflow at parse time, so every run that would have
used the default fails before any job starts.

#### Example: flagged

```yaml
name: Example
on:
  workflow_call:
    inputs:
      retries: {type: number, default: three}
jobs:
  build:
    runs-on: ubuntu-latest
    if: inputs.retries
    steps:
      - run: echo ok
```

#### Example: passes

```yaml
name: Example
on:
  workflow_call:
    inputs:
      retries: {type: number, default: 3}
jobs:
  build:
    runs-on: ubuntu-latest
    if: inputs.retries
    steps:
      - run: echo ok
```

#### When it does not fire

The default is an expression (`${{ ... }}`), the type is `string` or
undeclared, or the input belongs to an action (actions have no types).

#### Suppress

`# jobsworth-ignore input-default-type` on the default's line, or
`rules: { input-default-type: off }` in `.jobsworth.yml`.

#### Related

`call-input-type`.

## Family: calls

### call-input-unknown

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| calls | error | 0.1 | stable |

#### What it checks

A job with `uses:` pointing at a reusable workflow supplies `with.<name>`
but the callee declares no `<name>` under `on.workflow_call.inputs`.

#### Why it matters

GitHub rejects the caller at parse time. A misspelt input name is the
usual cause.

#### Example: flagged

```yaml
name: Example
on: push
jobs:
  call:
    uses: ./.github/workflows/reusable.yml
    with:
      env: prod
      evn: staging
```

#### Example: passes

```yaml
name: Example
on: push
jobs:
  call:
    uses: ./.github/workflows/reusable.yml
    with:
      env: prod
```

#### When it does not fire

The callee could not be loaded (fetch failure, skip list); the fetch
finding covers that. Dispatch-only inputs of the callee do not count as
declared for `workflow_call`.

#### Suppress

`# jobsworth-ignore call-input-unknown` on the `with` value's line, or
`rules: { call-input-unknown: off }` in `.jobsworth.yml`.

#### Related

`call-input-missing`, `call-input-type`.

### call-input-type

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| calls | error | 0.1 | stable |

#### What it checks

A literal passed in `with:` is not representable in the callee's declared
type: text for `number`, anything but a bare `true`/`false` for `boolean`,
or a value outside `options:` for `choice`.

#### Why it matters

GitHub rejects the caller at parse time. Quoted booleans (`"true"`) are
the classic case: YAML makes them strings.

#### Example: flagged

```yaml
name: Example
on: push
jobs:
  call:
    uses: ./.github/workflows/reusable.yml
    with:
      env: prod
      count: three
```

#### Example: passes

```yaml
name: Example
on: push
jobs:
  call:
    uses: ./.github/workflows/reusable.yml
    with:
      env: prod
      count: 3
      strict: ${{ github.event_name == 'push' }}
```

#### When it does not fire

The value is an expression, the callee type is `string` or undeclared, or
the callee could not be loaded.

#### Suppress

`# jobsworth-ignore call-input-type` on the `with` value's line, or
`rules: { call-input-type: off }` in `.jobsworth.yml`.

#### Related

`input-default-type`.

### step-input-type

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| calls | error | 0.2 | stable |

#### What it checks

A step passes a literal that does not fit the input's declared `type:`.
Only inputs that carry a `type:` are checked; plain `action.yml` inputs
are untyped strings.

#### Why it matters

The value is coerced or rejected at runtime.

#### Example: flagged

```yaml
name: Example
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/typed
        with:
          count: many
```

#### Example: passes

```yaml
name: Example
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/typed
        with:
          count: 3
```

#### When it does not fire

Untyped inputs, or an action that could not be loaded. An expression is
checked only when its inferred type is definite (a comparison, a number,
a JSON value); a string-shaped expression such as
`${{ github.run_number }}` may hold a number and passes.

#### Suppress

`# jobsworth-ignore step-input-type` on the `with` value's line, or
`rules: { step-input-type: off }` in `.jobsworth.yml`.

#### Related

`step-input-choice`.

### step-with-on-run

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| calls | error | 0.2 | stable |

#### What it checks

A `run:` step has a `with:` block.

#### Why it matters

The runner ignores `with:` on run steps; the values never reach the
script. Usually a step that was converted from `uses:` to `run:`.

#### Example: flagged

```yaml
name: Example
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: make
        with:
          target: all
```

#### Example: passes

```yaml
name: Example
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: make $TARGET
        env:
          TARGET: all
```

#### When it does not fire

`with:` on a `uses:` step.

### python-syntax

| Family | Default | Since | Status |
|--------|---------|-------|--------|
| scripts | warning | 0.4 | stable |

#### What it checks

A `shell: python` step whose body `ast.parse` rejects, when a python interpreter is on PATH (`scripts.python`).

#### Why it matters

The step fails at runtime. A warning, not an error, because the validator's interpreter may differ from the runner's.

#### Example: flagged

```yaml
name: Example
on: push
permissions: read-all
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - shell: python
        run: |
          def broken(:
              pass
```

#### Example: passes

```yaml
name: Example
on: push
permissions: read-all
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - shell: python
        run: |
          print("ok")
```

#### When it does not fire

Bodies that parse, and an absent interpreter.

#### Suppress

`# jobsworth-ignore python-syntax` on the line, or
`rules: { python-syntax: off }` in `.jobsworth.yml`.
